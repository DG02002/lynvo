## Generate the external Worker boilerplate

Paste this prompt into a coding agent from the directory where you want the project created. The agent should build the shared extractor infrastructure, not a finished source plugin.

Before you run it, replace `your_organization_name` and `your_extractor_name`. You can keep the example plugin until the Worker passes its contract tests.

<CodeBlock label="Agent prompt">

```text
Create a production-ready Lynvo external extractor Worker.

Project identity:
- Organization: your_organization_name
- Extractor name: your_extractor_name
- Extractor ID: com.your_organization_name.your_extractor_name

Use this stack:
- TypeScript with strict mode
- Cloudflare Workers
- Hono for HTTP routing
- Zod for every request and response boundary
- pnpm
- Vitest
- Wrangler configuration in wrangler.jsonc

Do not build a frontend. Do not add source-specific scraping to the route
handlers. Build a reusable extractor shell where developers can add plugins
later.

Implement Lynvo external extractor protocol version 1.0 over HTTPS and JSON.
The private @lynvo/extractor-protocol package is not available outside the
Lynvo monorepo, so define and test the required schemas locally.

Create these endpoints:
- GET /manifest: public
- POST /verify: bearer authentication required
- GET /usage: bearer authentication required
- POST /extract: bearer authentication required

Read the bearer key from EXTRACTOR_API_KEY. Support .dev.vars locally and a
Wrangler secret in production. Reject unauthorized requests before usage
reservation or upstream network access.

Design a plugin interface with:
- Stable id, displayName, version, and status
- Optional description, homepage, and direct HTTPS WebP iconUrl
- URL matchers for schemes, hosts, host patterns, and path patterns
- Declared password, lazy-node, and HTTP Basic Auth capabilities
- canHandle(input) for routing
- extract(context) for source-specific extraction

Create a plugin catalog as the single source of truth for manifest metadata
and request dispatch. The Hono route layer must not contain source-specific
conditions.

Add one clearly labeled example plugin for media.example.com. Keep it small
and deterministic so a developer can replace it with a real plugin. Document
exactly which files belong to the shared extractor and which belong to a
plugin.

The manifest must include:
- protocolVersion: "1.0"
- A stable namespaced extractorId
- A human-readable displayName
- auth.type: "bearer"
- usage.endpoint: "/usage"
- Non-empty matchers derived from the plugin catalog
- features for password, lazyNodes, and basicAuth
- extensions.lynvo.sources derived from the plugin catalog

Model extraction input as either:
- A source URL with kind: "source" and sourceUrl
- A lazy-node request with kind: "node", nodeUrl, and optional resourceId

Support optional sourceId, password, and basicAuth credentials. Never place
credentials in a target URL, response, manifest, or log.

Support these media node kinds:
- playable with label and URL
- group with label, children, and optional selectable
- resolvable with label, nodeUrl, and optional resourceId

Support optional node metadata used by Lynvo, including description,
thumbnail, size, MIME type, quality, duration, subtitles, audio tracks,
headers, and expiry when applicable. Validate URLs and recursive child nodes.

A successful extraction response must include:
- source.extractorId and source.displayName
- Optional sourceId, sourceName, sourceIconUrl, pageTitle, and audio summary
- A non-empty nodes array
- An extensions object

Return JSON protocol errors with a stable code and safe message. Implement:
- UNSUPPORTED_URL
- AUTH_INVALID
- AUTH_REQUIRED
- RATE_LIMITED
- TEMPORARY_FAILURE
- PERMANENT_FAILURE
- PASSWORD_REQUIRED
- INVALID_PASSWORD
- NODE_EXPIRED
- PROTOCOL_MISMATCH
- BAD_REQUEST

Implement finite usage reporting. GET /usage must return at least one metric
with id, label, used, limit, unit, period, and resetsAt. Reserve capacity
atomically before extraction, settle successful usage, and release failed
reservations. Use a Cloudflare Durable Object when concurrency requires shared
state. Do not use an in-memory counter as the production limiter.

Keep modules focused. Use a structure similar to:
- src/index.ts
- src/app.ts
- src/env.ts
- src/auth.ts
- src/manifest.ts
- src/protocol/schemas.ts
- src/protocol/errors.ts
- src/plugins/types.ts
- src/plugins/catalog.ts
- src/plugins/example-media.ts
- src/usage/limiter.ts
- tests/contract.test.ts
- tests/plugins/example-media.test.ts

Add contract tests for:
- Manifest schema and protocol version
- Duplicate plugin IDs
- Matcher and source metadata consistency
- Authentication on protected endpoints
- Malformed extraction requests
- Supported and unsupported URLs
- Every node kind
- Success response validation
- Every protocol error envelope
- Usage response validation
- Reservation settlement and release
- No credentials in responses or logs

Add README instructions for:
- Installing dependencies
- Running locally
- Setting EXTRACTOR_API_KEY
- Running tests and type checks
- Deploying with Wrangler
- Verifying all four production endpoints
- Adding a new plugin without editing the route layer
- Connecting the deployed origin and bearer key in Lynvo Settings

Use arrow functions, descriptive names, kebab-case files, and TypeScript
interfaces. Avoid type casts and duplicated schemas. Keep secrets out of source
control.

Run formatting, tests, type checking, and a Wrangler dry-run build. Fix all
failures before finishing. At the end, report:
1. The created file tree
2. The commands that passed
3. The environment variables and secrets still required
4. The exact files a developer edits to add the first real plugin
```

</CodeBlock>

The generated Worker should run before you add a real source. Replace the example plugin one source at a time, and keep its supported, unsupported, and failure fixtures beside the plugin.
