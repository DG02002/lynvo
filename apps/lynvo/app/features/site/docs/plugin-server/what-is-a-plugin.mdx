<DocSection id="what-is-a-plugin">

A Plugin is a Source-specific implementation hosted by a Plugin Server. It recognizes URLs from one Source, fetches the Source's data, and converts it into Media Nodes: playable items, folders, groups, and unresolved items.

For example, a Plugin may support a self-hosted file index. It matches that index's domain, handles its authentication rules, reads its folders and files, and returns playable items and unresolved items. The Plugin Server handles the shared protocol around that work.

## What a Plugin owns

A Plugin owns everything specific to its Source:

- Its stable Plugin ID, display name, version, status, and icon
- Host and path matchers
- Source-specific credentials
- Upstream requests and response parsing
- Playable item, folder, group, and unresolved item creation
- Source-specific errors and test fixtures

A Plugin does not implement bearer authentication, protocol routes, global usage enforcement, or Lynvo interface behavior. Those concerns stay in the Plugin Server runtime so every Plugin follows the same contract.

Register every user-visible Plugin under `extensions.lynvo.plugins` in the [manifest](/developer/manifest). Lynvo reads this catalog to show the Plugin in [Settings](/settings/plugins) and route supported URLs to the Plugin Server.

## How an Extraction flows

The Plugin Server is the deployed service. Plugins are the Source integrations that run inside it:

1. Lynvo matches a URL against the Plugin Server manifest
2. Lynvo sends the Extraction request to the Plugin Server
3. The Plugin Server authenticates and validates the request
4. The Plugin Server selects the matching Plugin
5. The Plugin converts the Source response into Media Nodes
6. The Plugin Server validates and returns the protocol response

To go deeper, use the [Media Node reference](/developer/media-nodes) when you replace the generated example, and the [route runtime reference](/developer/hono-routes) for the wiring around your Plugin.
