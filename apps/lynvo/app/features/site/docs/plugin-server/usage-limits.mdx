<DocSection id="usage-schema">

Usage limits are the finite metrics a Plugin Server reports at `GET /usage` and enforces before its work exceeds them. Every connected credential has at least one finite metric, and the server must enforce the limits it reports.

To report each independently enforced limit, return one metric record:

<CodeBlock label="GET /usage">

```json
{
  "metrics": [
    {
      "id": "extract-requests",
      "label": "Extract requests",
      "used": 84,
      "limit": 1000,
      "unit": "requests",
      "period": "monthly",
      "resetsAt": "2026-08-01T00:00:00.000Z"
    }
  ]
}
```

</CodeBlock>

Each metric must satisfy these invariants, which the protocol package's `validateUsageContract` and `parseUsageResponseContract` helpers check:

- `id` is unique within the response
- `used` is non-negative and no greater than `limit`
- `limit` is positive
- `period` is `daily` or `monthly`
- `resetsAt` is an ISO 8601 timestamp
- `pluginId` optionally scopes the metric to one Plugin's allowance

## Enforce the reported limits

Report the same allowances you enforce. Use a Cloudflare Durable Object for atomic reservations: reserve capacity before the adapter performs upstream work, settle the reservation after the adapter finishes, and release it when your accounting policy does not charge failed work.

When no capacity remains, return `RATE_LIMITED` from `/extract` with `error.retryAfterSeconds` and a matching `Retry-After` header so clients can wait until the limit resets:

<CodeBlock label="429 response">

```json
{
  "ok": false,
  "error": {
    "code": "RATE_LIMITED",
    "message": "Monthly extract request limit reached.",
    "retryAfterSeconds": 3600
  },
  "extensions": {}
}
```

</CodeBlock>

<DocsNote title="Use the reported limits">

Lynvo renders the metrics returned by your Plugin Server in [**Settings > Usage**](/settings/usage) and does not own third-party accounting. The message text above is an example; Lynvo maps the code to its own copy.

</DocsNote>
