The shared route runtime owns authentication, request validation, usage, and protocol response serialization, keeping all of it outside Source-specific code. The generated `src/index.ts` routes every required endpoint through `createPluginServerRuntime`:

<CodeBlock label="src/index.ts">

```ts
import {
  createPluginServerRuntime,
  ProtocolError,
  validUsageResponseFixture,
  validateBearerCredential,
} from "@dg02002/lynvo-plugin-server-protocol"

const runtime = createPluginServerRuntime<Env>({
  manifest,
  auth: {
    validate: ({ request, env }) =>
      validateBearerCredential(request, env.LYNVO_PLUGIN_SERVER_API_KEY),
  },
  usage: () => validUsageResponseFixture,
  extract: ({ target }) => {
    if (target.kind !== "url") {
      throw new ProtocolError(
        "UNSUPPORTED_TARGET",
        "This example only accepts URL targets."
      )
    }
    return extractExampleSource(target.url, manifest.pluginServerId)
  },
})

const app = new Hono<{ Bindings: Env }>()
app.get("/manifest", (context) =>
  runtime.handleManifest(context.req.raw, context.env)
)
app.post("/verify", (context) =>
  runtime.handleVerify(context.req.raw, context.env)
)
app.get("/usage", (context) =>
  runtime.handleUsage(context.req.raw, context.env)
)
app.post("/extract", (context) =>
  runtime.handleExtract(context.req.raw, context.env)
)
```

</CodeBlock>

Replace the manifest, the authentication function, usage accounting, and the Source implementation. Keep the four route handlers unchanged unless you need a protocol-level extension; when the manifest sets `features.discovery`, wire `runtime.handleDiscover` the same way.

## What the runtime maps for you

The runtime turns failures into protocol responses before and after your Plugin runs. An unexpected throw inside `extract` becomes a `TEMPORARY_FAILURE` with HTTP status 500, and a thrown `ProtocolError` becomes its documented status and a `Retry-After` header when it carries `retryAfterSeconds`. Before your Plugin runs, the runtime rejects:

- A rejected bearer key, as `AUTH_INVALID` 401 with the message `API key was rejected.`
- An unparseable JSON body, as `BAD_REQUEST` 400 with the message `Invalid JSON body.`
- A body that fails the request schema, as `BAD_REQUEST` 400 with the message `Invalid request body.`
- A URL or resource-ID target no matcher or Plugin accepts, as `UNSUPPORTED_URL` or `UNSUPPORTED_TARGET` 400 with the message `Unsupported extraction target by this Plugin Server: <target>`
- A manifest that fails validation, as `PROTOCOL_MISMATCH` 500 with the message `Plugin Server Manifest does not match protocol v1.`

The extraction callback receives a URL target or an opaque `resourceId` target. The starter handles URL targets only; add the Source-specific resource-ID branch if your Plugin emits unresolved items with `resourceId`.

The starter returns a finite usage fixture so its contract tests run without a database. Replace that fixture with durable accounting before deployment — see [usage limits](/developer/usage-limits).
