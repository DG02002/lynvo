# ADR 0002: Browser Convex authentication

- Status: Accepted
- Date: 2026-08-18
- Supersedes: The blanket prohibition on browser Convex access in repository guidance

## Context

Lynvo keeps its long-lived Convex Auth refresh token and access token in a Worker Auth Session Durable Object. The browser receives only an opaque `HttpOnly`, `Secure`, `SameSite=Lax` Lynvo session cookie. This protects refresh authority, but it also prevents the browser from using Convex subscriptions and causes Lynvo to duplicate database reactivity through Durable Objects, WebSockets, revisions, and reconciliation.

Convex Auth already issues RS256 JWT access tokens that Convex validates through the existing `convex/auth.config.ts` provider. Creating another application token format would duplicate identity and key management.

## Decision

The HttpOnly Lynvo session remains the session and refresh authority. A same-origin Worker endpoint validates that session and returns its short-lived Convex Auth access JWT. The endpoint rotates the access token through the server-held refresh token when the client forces a refresh. It is rate-limited, returns `Cache-Control: no-store`, and never includes tokens in logs or error payloads.

The browser holds the access JWT in JavaScript memory only. It is supplied to one browser-lifetime `ConvexReactClient` through `ConvexProviderWithAuth`. It is never placed in cookies, `localStorage`, IndexedDB, URLs, loader data, server-rendered HTML, analytics, or monitoring.

The JWT contract is:

- Issuer: the deployment-specific `CONVEX_SITE_URL`.
- Audience: `convex`, restricted by `convex/auth.config.ts`.
- Subject: the Convex Auth user and session identity generated by Convex Auth.
- Lifetime: five minutes.
- Signing algorithm: RS256.
- Signing keys: `JWT_PRIVATE_KEY` and the matching `JWKS` managed for the Convex deployment.
- Rotation: publish overlapping verification keys before issuing with a new private key; remove a retired verification key only after the five-minute token lifetime and operational clock-skew allowance have elapsed.
- Clock skew: Lynvo does not extend token lifetime. Convex owns JWT validation tolerance; deployments allow an additional five-minute operational overlap before retiring an old verification key.

Every authenticated browser-public Convex function derives identity from `ctx.auth.getUserIdentity()` through the shared authorization helper. Browser arguments never select an account identity.

## Revocation

Revoking a Lynvo session deletes the Worker-held refresh authority immediately, clears identity-bound browser state, and prevents another token refresh. A previously issued access token can remain valid for no more than five minutes. Immediate session-revocation messages remain on the Lynvo WebSocket because they are ephemeral security events, not database synchronization.

## Security consequences

JavaScript that executes in the Lynvo origin can read the in-memory access token, so Content Security Policy and XSS prevention remain security boundaries. The token has a narrow audience and short residual lifetime, while the more powerful refresh token remains inaccessible to browser JavaScript.

Reloading or closing the page naturally removes the access token. A reload with a valid HttpOnly session obtains a new access token from the Worker. A 401 from the token endpoint signs the browser out; bounded 5xx recovery enters an unavailable state instead of retrying indefinitely.

## Rejected alternatives

- Persisting Convex Auth tokens with its browser storage adapter would expose the refresh token to JavaScript-readable storage.
- Minting a second Lynvo-specific JWT would duplicate Convex Auth identity, signing, rotation, and validation.
- Keeping the custom database synchronization protocol as a fallback would preserve two realtime owners and violate the target architecture.
